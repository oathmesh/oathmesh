# OathMesh Key Rotation Runbook (Zero-Downtime)

This runbook is for rotating the issuer signing key without service interruption, using current OathMesh behavior:

- Issuer signs with one active private key loaded from `OATHMESH_PRIVATE_KEY` / `OATHMESH_PRIVATE_KEY_B64` / `OATHMESH_PRIVATE_KEY_FILE`.
- `kid` is generated by the issuer at startup.
- Receivers cache JWKS (`OATHMESH_JWKS_CACHE_TTL`) and re-fetch on `kid` miss.
- Token lifetime is short (max 300s).

---

## 1) Prechecks

1. Confirm issuer health:
   - `GET /healthz` = `200`
   - `GET /.well-known/jwks.json` returns at least 1 key
2. Record current JWKS `kid` values.
3. Confirm receiver settings:
   - `OATHMESH_JWKS_CACHE_TTL` is known (recommended `<=60` during rotation window)
   - receivers are healthy and can reach issuer JWKS endpoint
4. Confirm token TTL policy:
   - `OATHMESH_TTL_MAX <= 300` (expected default)
5. Ensure rollback access:
   - previous private key secret available
   - ability to roll issuer back quickly

---

## 2) Staged Rollout (No-Downtime Strategy)

### Stage A — Prepare new key material (no traffic impact)

1. Generate a new Ed25519 keypair with `scripts/rotate-key.ps1`.
2. Store new private key in your secret manager **without** applying it to issuer yet.
3. Keep current key secret unchanged and issuer running.

### Stage B — Receiver/JWKS cache prep

1. Before cutover, reduce receiver `OATHMESH_JWKS_CACHE_TTL` to `30-60` seconds if currently higher.
2. Roll receivers (if needed) so new TTL is active.
3. Wait one full old TTL period so stale caches age out.

### Stage C — Issuer cutover

1. Update issuer secret to new private key value.
2. Roll issuer instances with standard rolling strategy (keep capacity during restart).
3. Verify issuer JWKS now publishes a new `kid`.

### Stage D — Overlap period

Because OathMesh tokens are short-lived (max 300s), use a **time overlap window**:

- Keep heightened monitoring for at least:  
  `overlap = OATHMESH_TTL_MAX + receiver OATHMESH_JWKS_CACHE_TTL + clock skew buffer`  
  (practical minimum: `~6-10 minutes`)
- During this period, expect mixed old/new tokens in flight; receivers should re-fetch JWKS on `kid` miss.

After overlap, restore receiver JWKS TTL to normal steady-state value (for example `300` if that is your standard).

---

## 3) Verification Checklist

- [ ] New private key generated and stored securely (not committed).
- [ ] Issuer secret updated manually (no automation writing secrets from script).
- [ ] Issuer `/healthz` healthy after rollout.
- [ ] Issuer JWKS reachable and contains a **new** `kid`.
- [ ] No sustained spike in verification failures (`issuer_untrusted`, signature errors).
- [ ] Receiver success rate remains within SLO during overlap window.

### Suggested checks

1. Fetch current JWKS kids:
   - `.\scripts\rotate-key.ps1 -Mode Check -IssuerUrl https://issuer.example.com`
2. Compare with pre-rotation kids:
   - `.\scripts\rotate-key.ps1 -Mode Check -IssuerUrl https://issuer.example.com -PreviousKids "kid1,kid2"`

---

## 4) Rollback Path

Use rollback if verification failures are sustained beyond the overlap window, or issuer health degrades.

1. Reapply previous private key secret.
2. Roll issuer back to last known-good revision/config.
3. Confirm JWKS returns prior `kid`.
4. Keep receiver JWKS TTL low (`30-60`) until stable.
5. Re-run verification checks and incident review before attempting rotation again.

---

## 5) Post-Rotation Checks

1. Observe for at least 2x overlap window:
   - issuer uptime/latency/error rate
   - receiver verification error rate
2. Confirm no unexpected `kid` churn (frequent issuer restarts can cause unnecessary `kid` changes).
3. Restore temporary operational settings (e.g., receiver cache TTL) to normal.
4. Record:
   - rotation time
   - old/new JWKS `kid`
   - operator
   - rollback readiness status

---

## Assumptions / Limitations

- Current issuer behavior generates `kid` at startup; operators cannot pre-set the exact `kid`.
- This runbook avoids direct cloud secret writes by design; secret update is an explicit manual operator step.
- For emergency compromise response, set receiver JWKS TTL as low as operationally possible before cutover.
