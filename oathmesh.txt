⸻

1. Executive summary

Oathmesh is a lightweight protocol and product for replacing shared machine secrets with short-lived signed call identity.

It is built for:
	•	agents
	•	CI/CD jobs
	•	internal tools
	•	automation bots
	•	service-to-service calls
	•	MCP-adjacent tool backends
	•	internal APIs

Oathmesh does not try to be a full service mesh, full IAM platform, or full OAuth replacement.

Its job is much narrower and much more valuable:

Mint, attach, verify, authorize, audit machine calls.

That focus fixes the main weakness in the earlier version of the idea. The product is no longer “general infra.” It is now a very specific security and developer-experience wedge:

Oathmesh replaces shared API keys and long-lived machine secrets with short-lived signed identity for agents, CI, and internal tools.

That is the product, the protocol, and the business.

3. The problem Oathmesh solves

Modern teams have too many machine callers:
	•	GitHub Actions workflows
	•	deployment bots
	•	internal scripts
	•	admin tools
	•	LLM agents
	•	MCP-style tool clients
	•	cron jobs
	•	background workers

Most of these callers still use weak authentication patterns:
	•	shared API keys
	•	copied bearer tokens
	•	overly broad cloud credentials
	•	static secrets in repos or CI variables
	•	internal-only trust assumptions
	•	poor audit trails

This creates five painful problems:

3.1 Shared secret sprawl

The same API key gets reused by multiple jobs, tools, and environments.

3.2 Missing caller identity

The receiver often knows only that “some token” was used, not which workflow, job, agent, or bot actually made the call.

3.3 Long-lived credentials

Secrets live too long and spread too far.

3.4 Weak authorization context

Receivers lack useful attributes like:
	•	workflow
	•	repo
	•	cluster
	•	environment
	•	delegating user
	•	reason for call

3.5 Bad auditability

Teams cannot answer:
	•	who called this API
	•	from where
	•	under whose authority
	•	for what operation
	•	why it was allowed

Oathmesh solves those five problems without forcing customers to deploy a full IAM stack or service mesh.

4. Product definition

4.1 What Oathmesh is

Oathmesh is two things:

A. A protocol

A small standard for signed short-lived machine call assertions.

B. A product

A developer-friendly issuer, verifier, gateway, SDK set, and audit platform built around that protocol.

4.2 What Oathmesh is not

Oathmesh is not:
	•	a full user authentication system
	•	a browser login platform
	•	a human consent system
	•	a service mesh dataplane
	•	a replacement for cloud IAM
	•	a replacement for OAuth for user-facing apps
	•	a replacement for SPIFFE, though it can sit beside it

4.3 The core promise

Every machine call should carry:
	•	identity
	•	intent
	•	target audience
	•	freshness
	•	provenance
	•	policy-evaluable context

5. Product principles

Oathmesh must follow these design principles.

5.1 Small core

The protocol must stay narrow and easy to implement.

5.2 Short-lived by default

Tokens should expire quickly.

5.3 Local verification

Receivers should verify without a network round-trip on every request.

5.4 Receiver-local authorization

Authentication is portable. Authorization is local.

5.5 Great developer experience

Integration should feel like adding middleware, not deploying a platform.

5.6 Strong auditability

Every allow or deny should be explainable.

5.7 Easy bootstrap

The first demo should work in under 15 minutes.

7. Final product architecture

7.1 Logical components

Issuer

Creates and signs Oath tokens.

Caller

The agent, workflow, bot, service, or tool client making the request.

Receiver

The API, tool server, or gateway accepting the request.

Verifier

The middleware or proxy logic that validates the token.

Policy engine

Evaluates whether the verified request is allowed.

Audit pipeline

Records verification and authorization outcomes.

7.2 Core flow
	1.	Caller authenticates to the issuer.
	2.	Caller requests a short-lived Oath token.
	3.	Issuer signs the token.
	4.	Caller attaches token to request.
	5.	Receiver verifies token.
	6.	Receiver evaluates local policy.
	7.	Receiver allows or denies.
	8.	Receiver emits structured audit event.

7.3 Golden path

The first and strongest Oathmesh workflow is:

GitHub Actions -> Oathmesh Issuer -> Internal API

That is the MVP wedge because it is:
	•	common
	•	painful
	•	easy to explain
	•	easy to demo
	•	immediately valuable

9. Oath Token specification

9.1 Token format

Oathmesh v1 uses a signed compact JWS/JWT.

This is practical because it is:
	•	widely supported
	•	easy to verify
	•	easy to cache keys for
	•	easy to implement in multiple languages

9.2 Header

Example:

{
  "typ": "om+jwt",
  "alg": "EdDSA",
  "kid": "issuer-key-2026-01"
}

9.3 Required claims

Every Oath Token must include:

{
  "iss": "https://issuer.oathmesh.dev",
  "sub": "agent://repo/acme/deploy-bot",
  "aud": "https://inventory.internal",
  "act": "inventory.write",
  "iat": 1774911000,
  "exp": 1774911120,
  "jti": "uuid"
}

Claim meanings

iss
Issuer identity.

sub
Caller identity.

aud
Intended receiver identity.

act
Requested operation family.

iat
Issued-at timestamp.

exp
Expiry timestamp.

jti
Unique token ID.

9.4 Optional claims

Optional but useful claims:

{
  "scope": ["inventory.read", "inventory.write"],
  "reason": "sync catalog after deploy",
  "src": {
    "type": "github_actions",
    "repo": "acme/storefront",
    "workflow": "deploy.yml",
    "run_id": "123456",
    "sha": "abc123"
  },
  "delegated_by": "user://mustafa",
  "env": "prod",
  "tenant": "acme-prod",
  "rqh": "sha256:request_hash_here"
}

9.5 Recommended subject schemes

To keep policies clean, Oathmesh should standardize identity URI shapes.

Recommended formats:
	•	svc://namespace/name
	•	agent://repo/org/name
	•	job://scheduler/name
	•	tool://runtime/client
	•	user://id

This fixes a key long-term protocol weakness: messy identity formats.

11.2 Metadata shape

12. Verification rules

Every conformant receiver must perform these checks:
	1.	parse token
	2.	identify issuer
	3.	load trusted issuer configuration
	4.	load or refresh JWKS
	5.	verify signature
	6.	verify issuer exact match
	7.	verify expiry
	8.	verify issued-at
	9.	verify audience
	10.	verify required claims
	11.	verify binding if present
	12.	check replay controls if enabled
	13.	evaluate local policy
	14.	emit audit event

12.1 Hard rejection conditions

Reject if:
	•	signature is invalid
	•	issuer is unknown
	•	token is expired
	•	audience is wrong
	•	algorithm is not allowed
	•	required claim is missing
	•	replay is detected
	•	policy denies request

12.2 Verification result

The receiver should expose a normalized object to app code:

{
  "principal": {
    "issuer": "https://issuer.oathmesh.dev",
    "subject": "agent://repo/acme/deploy-bot"
  },
  "action": "inventory.write",
  "scope": ["inventory.write"],
  "source": {
    "type": "github_actions",
    "repo": "acme/storefront",
    "workflow": "deploy.yml"
  },
  "token_id": "uuid"
}

This is the Verified Caller Context.

13. Authorization model

13.1 Oathmesh rule

The token proves identity and context.
The receiver decides permission.

13.2 v1 policy model

The first policy model must be intentionally simple.

Supported inputs:
	•	issuer
	•	subject
	•	audience
	•	action
	•	scope
	•	source attributes
	•	environment
	•	request path
	•	method

13.3 Example policy

version: 1

issuers:
  - https://issuer.oathmesh.dev

audiences:
  - https://inventory.internal

rules:
  - name: storefront-read
    match:
      sub: "agent://repo/acme/*"
      act: "inventory.read"
    allow: true

  - name: deploy-write
    match:
      sub: "agent://repo/acme/deploy-bot"
      act: "inventory.write"
      src:
        type: "github_actions"
        repo: "acme/storefront"
        workflow: "deploy.yml"
    allow: true

  - name: default
    allow: false

13.4 Policy philosophy

The first version should be:
	•	readable
	•	explicit
	•	default deny
	•	file-based
	•	easy to debug

Do not start with a complex policy language.

This fixes a major earlier risk.

14. Security model

14.1 Security objectives

Oathmesh is designed to reduce:
	•	shared secret risk
	•	replay risk
	•	impersonation by copied API keys
	•	weak provenance
	•	poor auditability

14.2 Required defaults

Production defaults should be:
	•	default TTL: 120 seconds
	•	maximum TTL: 300 seconds
	•	default deny policy
	•	trusted issuers must be explicit
	•	full token logging disabled
	•	replay cache on write actions enabled
	•	request binding supported
	•	JWKS caching enabled
	•	EdDSA preferred

14.3 Threat model

Threat: stolen token

Mitigation:
	•	short TTL
	•	optional request binding
	•	optional replay detection

Threat: replay

Mitigation:
	•	jti
	•	replay cache
	•	request-hash binding
	•	low TTL

Threat: compromised issuer key

Mitigation:
	•	key rotation
	•	KMS/HSM support
	•	trust removal
	•	deny by kid

Threat: overbroad subject

Mitigation:
	•	standardized subject URIs
	•	narrow policy matching

Threat: confused deputy

Mitigation:
	•	audience enforcement
	•	receiver-local authorization
	•	source-aware policy

Threat: forged provenance

Mitigation:
	•	provenance is trusted only if issuer attests it from trusted bootstrap
	•	not from caller-provided freeform input alone

Threat: log leakage

Mitigation:
	•	never log full tokens by default
	•	log claim summary only

Threat: gateway trust boundary confusion

Mitigation:
	•	normalize verified identity context
	•	sign or harden internal trust headers if forwarded

This fixes the earlier credibility gap around security maturity.

The MVP must prove one simple story:

A CI workflow can call an internal API without a shared static secret, and the API can see exactly who called it and why it was allowed.

16.2 MVP scope

The MVP includes only:

Issuer
	•	mint API
	•	JWKS
	•	metadata endpoint
	•	local dev mode
	•	GitHub Actions bootstrap

Verifier SDK
	•	Node.js middleware
	•	Python middleware

Gateway
	•	small reverse proxy mode
	•	verifies token
	•	forwards verified context

Policy
	•	YAML policy file
	•	default deny
	•	allow by subject/action/source

Audit
	•	JSON audit logs
	•	allow/deny events
	•	token ID correlation

CLI
	•	oathmesh mint
	•	oathmesh verify
	•	oathmesh inspect

16.3 MVP non-goals

Do not include:
	•	GUI policy editor
	•	enterprise SSO
	•	advanced delegation graph
	•	multi-cloud bootstrap on day one
	•	full K8s operator
	•	revocation service
	•	billing engine complexity

16.4 MVP demo flow
	1.	GitHub Action runs.
	2.	It exchanges bootstrap identity for Oath Token.
	3.	It calls internal API.
	4.	API verifies token.
	5.	API matches policy.
	6.	Audit log shows:
	•	subject
	•	repo
	•	workflow

26. Final weaknesses and fixes

Here is the final clean list of weaknesses and how they are resolved.

Weakness 1: The idea was too broad

Fix: narrowed to short-lived signed identity for agents, CI, and internal tools.

Weakness 2: “Mesh” suggested the wrong category

Fix: define clearly that Oathmesh is not a service mesh; it is a machine-call identity protocol.

Weakness 3: The protocol tried to do too much

Fix: move advanced items to later phases; keep v1 very small.

Weakness 4: Policy risked becoming too complex

Fix: file-based allow/deny policy only in v1.

Weakness 5: Naming was slightly poetic

Fix: product = Oathmesh, token = Oath Token, result = Verified Caller Context.

Weakness 6: Monetization was vague

Fix: managed issuer + audit console is the first paid product.

Weakness 7: Marketing was too abstract

Fix: lead with replacing shared machine secrets.

Weakness 8: MVP was not sharp enough

Fix: GitHub Actions to internal API is now the golden path.

Weakness 9: Security credibility needed work

Fix: add explicit threat model, defaults, and verification rules.

Weakness 10: Ecosystem scope was muddy

Fix: treat MCP as a use case and channel, not the center of the protocol.
